# 加速器、存储层级与 Roofline

“模型是计算 bound 还是显存 bound”只是起点。真实 kernel 还可能受共享内存、指令发射、指数单元、同步、主机提交或跨卡链路限制。

## 1. Roofline 给出上界，不给出成绩

算术强度是每读取一字节数据执行的浮点运算数。 attainable performance 满足：

$$P_{attainable}\le\min(P,R I)$$

$P$ 是峰值算力，$R$ 是带宽，$I$ 是算术强度。低强度时增加 TFLOPS 没用，高强度时增加带宽也未必有用。

但应用 Roofline 前要统一口径：数据量是否包含读写、是否只统计 DRAM、算力是否对应实际数据类型与稀疏能力、kernel 是否达到峰值。将 L2 命中流量当 DRAM 流量，会得出错误结论。

## 2. 容量、带宽和延迟是三件事

- 容量：权重、KV、激活是否放得下；
- 带宽：单位时间能传多少字节；
- 延迟：发起一次访问到数据可用要多久；
- 并发：同时能维持多少未完成事务。

依据 Little 定律，在途字节数约等于吞吐乘延迟。若每个请求 $s$ 字节、延迟 $L$、可维持 $N_o$ 个请求：

$$R_{effective}\le\min\left(R_{interface},\frac{N_os}{L}\right)$$

提高接口带宽但不增加在途请求，实际吞吐可能几乎不变。这也是大 tile 提高复用却可能降低性能的原因：驻留块变少，内存级并行下降。

## 3. 数据复用同时影响能耗

寄存器、shared memory、L2、HBM 和远端内存每次访问的能量不同。减少 DRAM 重读不仅省时间，也常显著省能量。

书稿以 Qwen3-8B、单请求 8K decode 为例估算约 0.534 J，其中权重读取约占 90%。这说明 decode 的优化重点常不是“把矩阵乘再快一点”，而是：

- 增加权重在批次内的复用；
- 避免权重和 KV 多层重复搬运；
- 在容量允许时选择合理精度；
- 减少小 kernel 和中间张量往返。

能耗数字依赖硬件与工艺假设，应作为分账方法而不是跨设备固定常数。

## 4. 持续性能受功率约束

峰值 TFLOPS 通常是在特定电压、频率、数据类型和功耗条件下给出。功率封顶时，芯片可能降频，持续算力低于峰值。

因此利用率需要说明分母：是营销峰值、当前频率下可持续峰值，还是某 kernel 的实测上限。长时间训练与推理更应关注持续性能和每焦耳产出。

## 5. 流水与双缓冲

将加载、计算、写回重叠后，完成节奏由最慢资源决定。双缓冲让计算当前块时加载下一块，但：

- 缓冲区不足会暴露延迟；
- 缓冲区过大会减少可用于 tile 的空间；
- 资源已经连续工作时再增加槽位无收益；
- 同步和地址交换仍有成本。

Attention kernel 还需要同时配平矩阵单元、shared memory 接口、指数/向量单元和寄存器压力。只优化矩阵乘，瓶颈会转移到 Softmax 或数据搬运。

## 6. die、节点与网络局部性

跨 die、跨 NUMA、跨卡访问不应视作等价内存。数据放置要比较：

- 本地 HBM 容量与远程容量；
- 链路带宽和延迟；
- 通信次数与消息大小；
- 集合通信拓扑；
- 一致性、页迁移和同步开销。

消息传输可粗写为：

$$T=\alpha+\frac{V}{R}$$

$\alpha$ 是固定开销，$V$ 是字节数，$R$ 是有效带宽。小消息由启动和协议开销主导，大消息才更接近带宽模型。NVLink 的存在不意味着任意小通信都便宜。

## 7. 从理论到实测的校准顺序

1. 确认 FLOPs 和字节数统计口径。
2. 单独测带宽、矩阵乘和关键 primitive。
3. 用 profiler 区分 DRAM、L2、shared memory 和计算单元。
4. 拆开 kernel 执行、launch、主机提交、同步和通信等待。
5. 检查功率、频率和热状态。
6. 最后才讨论“架构 inefficiency”。

若端到端慢但 kernel 很快，问题可能在图外；若 kernel 慢，也要判断是没达到 Roofline，还是 Roofline 输入本身算错。
