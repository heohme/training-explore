# 负载、排队与 SLO

一次 benchmark 的 token/s 不是服务容量。线上容量还取决于请求何时到达、输入输出多长、是否带工具等待、状态占显存多久，以及失败请求消耗了多少资源。

## 1. 先拆开用户等待

一次生成至少包含：

- 排队与调度：请求已到，但没有获得执行槽位；
- 前缀处理：读取或计算输入上下文，影响 TTFT；
- 逐 token 生成：决定 token 间隔和完整请求时延；
- 网络与流式传输：影响用户看到输出的时间；
- 工具、环境和重试：Agent 请求还会多次回到模型。

因此至少同时观察 TTFT、TPOT/逐 token 间隔、完整请求延迟、吞吐和 p95/p99。降低队列等待可能让 decode batch 更大，却使单 token 间隔变差；提高单请求速度也可能降低总吞吐。

SLO 应写成可测量句子，例如“给定输入长度和并发分布，p95 TTFT 小于某值，p95 逐 token 间隔小于某值，错误率低于某值”，而不是“系统要快”。

## 2. 状态驻留也是成本

KV Cache 不只由最终大小决定，还由驻留时间决定：

$$A_M=\int M(t)\,dt$$

单位可以是 GiB·s。两个请求最终 KV 相同，一个持续 1 秒，一个因工具调用持续 30 秒，对并发容量的影响完全不同。

Agent 在工具执行期间可能保留：

- 模型 KV 和采样状态；
- 调度槽位或连续批处理位置；
- 会话对象和工具结果；
- 多轮分支、草稿或回滚状态。

优化吞吐时要把“计算中”和“等待但仍占资源”分开。否则 GPU 利用率看似不高，显存却无法接收新请求。

## 3. 到达过程决定排队

离散时间流体队列可写为：

$$Q_{k+1}=\max(0,Q_k+A_k-\mu_k\Delta t)$$

$A_k$ 是区间新增工作量，$\mu_k$ 是可处理速率。即使长期平均 $\mu$ 足够，突发到达、长输入集中出现、输出长度差异和维护窗口仍会积压。

“平均每秒 10 请求”没有说明：

- 10 个请求是均匀还是同一时刻到达；
- 每个请求输入是 100 还是 100K token；
- 输出是短答案还是长思维链；
- 是否同时发生工具等待；
- 缓存命中是否相关。

容量测试必须保留请求组成和到达分布。

## 4. 前缀复用有明确边界

若请求总输入为 $I_i$，命中前缀 $K_i$，需要新计算的前缀为：

$$P_i=I_i-K_i$$

它减少的是新输入的重算，不会消除：

- 已命中 KV 的显存占用；
- decode 每步对旧 KV 的读取；
- 新 token 对完整可见历史的 Attention；
- 前缀索引、查找、换入和一致性问题。

共享前缀越靠近请求开头越容易复用；中间插入动态内容会破坏后续命中。KV 放在 CPU 或远端缓存还要支付传输和恢复时间。

## 5. 成功任务成本

若每次尝试成本为 $c$，成功率为 $p$，忽略相关重试时成功任务期望成本为：

$$C_{success}=\frac{c}{p}$$

这里 $c$ 应包含失败生成、丢弃输出、工具调用、环境运行、验证和人工接管。单次 token 更便宜但成功率下降，成功任务反而可能更贵。

对于多步 Agent，还要分析：

- 哪些步骤串行处于关键路径；
- 哪些工具调用可并行；
- 重试是否放大下游成本；
- 上下文增长是否让后续每步更贵；
- 早停和验证能否减少无效分支。

Amdahl 定律仍然适用：模型调用只占总时长一部分时，单纯加速模型存在上限。

## 6. 负载分层

| 负载 | 主要特征 | 更适合的观察方式 |
|---|---|---|
| 单轮在线推理 | 低延迟、连续 decode | TTFT/TPOT、并发、队列 |
| 离线批量生成 | 可排队、吞吐优先 | 总完成时间、单位样本成本 |
| 长上下文检索/Agent | 状态驻留、工具等待、前缀复用 | 会话级资源时间、关键路径 |
| 训练 | 大矩阵、频繁同步 | MFU、step time、网络/IO |
| RL 后训练 | 生成、评分、更新交替 | 全周期时间、样本有效率 |

把在线服务和 RL rollout 混在一个“tokens/s”指标里，会漏掉最重要的成本。

## 7. 一个可复现的容量报告

至少记录模型与精度、硬件、并行方式、输入/输出分布、到达过程、缓存命中、并发策略、工具等待、成功标准、SLO 分位数和失败成本。报告原始轨迹而不只报均值，才能发现长尾和排队。
